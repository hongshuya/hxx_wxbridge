# 技术笔记

这份笔记记录的**不是设计，而是排查结论**——每一条都对应一次"以为能行、实测不行"的过程。
如果要移植到别的微信版本，先看这里。

## 1. 为什么不用现成的自动化方案

微信 PC 4.1.15 上，主流路线全部堵死：

| 路线 | 结果 |
|---|---|
| UIAutomation（`wx4py` / `wxauto` / `uiautomation`） | **主窗口里没有控件树** |
| 协议库 / Pad 协议 | 不支持 4.1.15；且需要第三方服务，风控风险大 |
| DLL 注入 / QAccessible | 需要微信自己开 accessibility，等于注入，不做 |

实测证据（探针见 `probes/`）：

- `probe15-enum-hwnd.py`：真递归枚举小号微信进程的**全部** HWND（含隐藏、深度 30、上限 500），
  主窗口 `Qt51514QWindowIcon` 的子节点数 = **1**（只有 `MMUIRenderSubWindowHW` 自己）。
  整个进程里没有任何可访问的控件内容。
- 老版本（≤4.0.3）主窗口类名是 `QMainWindow`（Qt Widgets，每个控件一个 HWND，UIA 可遍历）；
  4.0.5+ 变成 `Qt51514QWindowIcon`——**Qt Quick/QML 用 GPU 渲染到一张画布**，控件不是窗口。
- 环境变量（`QT_OPENGL=software` / `QT_ANGLE_PLATFORM=software` / `QSG_RENDER_LOOP=basic`）
  也救不回来：安装目录里**根本没有 `opengl32sw.dll`**，那些开关是空转。

结论：只剩"把它当画面看"这一条路。

## 2. 抓帧：PrintWindow 与 WGC 的取舍

- `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT=2)` **能**抓到 Qt Quick 窗口（`nonblack_ratio 1.0`），
  但——**窗口被完全遮挡时返回全黑**（实测：用户全屏看视频，所有微信窗口亮度全 0；
  用 `SetWindowPos(..., HWND_TOPMOST, SWP_NOACTIVATE)` 提层也没用）。
- `Windows.Graphics.Capture`（`windows-capture`）**能在被遮挡时抓**，是本项目的主力后端；
  但有机器上 `CreateForWindow` 会抛 `Failed to convert item to GraphicsCaptureItem`，
  所以 `capture: auto` 会自动降级到 printwindow。
- **WGC 帧 = 应用逻辑画布 × DPI 缩放**，不是窗口尺寸：小号主窗口外框 613x647、
  客户区 880x722（曾用 `MoveWindow` 放大过）、WGC 帧 **1102x904**（= 880x722 × 1.2525，125% 缩放）。
  PrintWindow 帧则贴合窗口尺寸、右侧会被裁掉。**两个后端的帧尺寸不一样，坐标换算必须逐帧算。**

## 3. 三套坐标系

这是踩得最久的坑，取坐标前先问自己"这是哪套坐标系"：

| 坐标系 | 来源 | 换算 |
|---|---|---|
| 帧坐标 | 截图后的像素（WGC: 客户区×DPI；PrintWindow: 整窗） | 到客户区：`client = frame * client_size / frame_size` |
| 客户区坐标 | `GetClientRect`，喂给 `PostMessage(WM_LBUTTONDOWN)` | 到屏幕：`ClientToScreen` |
| 屏幕坐标 | 真键鼠 `SetCursorPos` / `WM_MOUSEWHEEL` | — |

教训：给 `click()` 之类的封装**同时**支持两种输入最容易出事（一处减掉边框偏移、
另一处没减 → 点击落到客户区之外 → 微信直接忽略，表现为"点了没反应"）。
现在分成了 `click_client()` / `real_click_client()`（客户区）与 `click()` / `real_click()`（帧/整窗）。

## 4. 输入：PostMessage 能干与不能干的事

Qt Quick 的消息处理有两道门，两道门都得过：

1. **窗口必须有焦点**，否则 Qt 直接丢掉键盘消息（`WM_CHAR` / `WM_PASTE` 全扔）。
2. 鼠标消息（`WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP`）**不需要焦点**就能点中。

所以"无焦点发送"的做法是：鼠标用 posted 消息点输入框，键盘前先
`AttachThreadInput(前台线程, 本线程, True)` → `SetFocus(hwnd)` → 解除。
**只给焦点、不调 `SetForegroundWindow`**，窗口的 Z 序不变、不会跳到最上层——
用户对这个非常敏感（"你每次看消息回消息都把窗口拉到最上层"）。

其他实测结论：

- **posted 的 `WM_LBUTTONDBLCLK` 不够**：微信 4.x 的"双击在新窗口打开会话"只认**系统级**
  双击（真实 `mouse_event` 序列）。要开独立窗口得用真键鼠双击。
- **posted 的 `Ctrl+V` 只会打出一个字母 `v`**：Qt 不认 posted 的修饰键状态。
  要粘图/粘文本请用 `WM_PASTE`（`post_paste()`），或走剪贴板 + `WM_PASTE`。
- `SetForegroundWindow` 在前台锁下会**调用成功但前台不变**——此后真键鼠全打到了别的窗口
  （实测把内容打进了用户的浏览器）。所以真键鼠路线之前必须先 `GetForegroundWindow() == hwnd`
  校验，不是就**宁可不发**。

## 5. 读消息：OCR 不是"识别文字"那么简单

- **行切分**：会话列表的行高固定（~81px），但群预览会折成两行，用"相邻块 y 间距 ≤40 聚类"
  会把群行跟下一行粘在一起（表现为**群永远发现不了**）。改用**按行首切**：
  `pitch = 0.55 * 行高`，只有比上一个行首低 pitch 以上的块才算新行。
- **名单里别带时间戳**：同一行的时间戳 x 坐标在名字右边，用 `TIME_RE` 剔掉，否则名字会读成
  `某群(38°41'N,11..．18:34` 这种。名字匹配用"包含关系"，不用相等。
- **昵称里的省略号**：微信会把长名字截断成 `某个很长的群名(38°41′N,11..`，所以匹配要模糊。
- **指纹归一**：消息里带图片时，气泡文本里是**本地文件路径**，而每次裁图有几个像素抖动 →
  文件名每轮都变 → 指纹每轮都变 → "这条回过了吗""这个骰子掷过了吗"全部失效
  （表现为群里每 3 秒重掷一次骰子）。现在把路径替换成 `[图片]`、再抹掉所有标点空白与
  `共 N 条` 横幅，指纹才稳定。
- **未读红点**：头像右上角 `x ∈ [0.12w, 0.19w]`，判据 `r>185 and g<95 and b<95`；
  被绿色数字气泡盖住时要补绿色判据。

## 6. 不重复发送（最贵的一课）

"发送成功了吗"这个自检一旦假阴性，就会出现**同一条消息发两遍**（posted 一遍、
真键鼠兜底一遍），用户截图抓个正着。根因有三个，都修了：

1. 自检拿原文前 8 个字去截图里找 → OCR 中文长句必有错字 → 假阴性。
   改成归一化后取前 10 字做子串匹配。
2. 刚发出的气泡常被输入框压掉一半 → 用 `y < h*(1-输入框比例)` 过滤等于把它排除掉。
   下界放宽到 `0.97h`。
3. 发送与自检不在同一个窗口上做（命令通道没切窗口）→ 换了窗口自然找不到。

现在 `send_text` 是三态判定，**永不重打**：

```
字在聊天区（'chat'）  → 发出去了，结束
字在输入框（'input'） → 只补一个回车（补空回车微信不会发空消息）
两处都没有            → 再看"聊天区消息条数有没有变多"这个旁证
                        变了 → 当已发送，绝不重发
                        没变 → 才允许换 WM_PASTE 路线重试一次
```

输入框里"有没有残留字"比"聊天区能不能找到"稳得多——别问"发出去了吗"，
问"字还在不在输入框里"。

## 7. 完整性级别：为什么"截图全黑"有时是环境问题

Windows 的完整性级别（IL）会限制跨进程操作：

- 低完整性（低沙箱，实测 `4096`）：**`PrintWindow` 抓别的进程窗口必然全黑**，
  进程内 WMI 也看不到别的进程（`Get-CimInstance` 恒返回 0 个 `Weixin.exe`）。
- 中完整性（正常用户态，`12288`）：能抓、能看到全部进程。

所以桥运行时会先 `my_integrity()` 自检并打日志；守护进程在低完整性下**直接退出、不占坑**
（否则会留下一个"活着但截不了图"的假守护）。看门狗也因此改成**看心跳文件的 mtime**
而不是扫进程列表（扫进程在不同完整性级别下结果不同，实测任务计划里能看到、
低沙箱 shell 里恒为 0）。

## 8. 状态与心跳

- `wxbridge.log`：只写状态变化 + 每 10 分钟一条心跳；命令通道的结果在 `wxbridge-cmd.out`。
- `wxbridge-supervisor.pid`：守护进程的 pid，每轮 `os.utime` 刷新 mtime 当心跳；
  超过 180 秒算过期（pid 复用会骗过 `pid_alive`，mtime 不会）。
- `wxbridge-cmd.txt`：一行一条命令，桥轮询执行——改代码后写 `reload`，
  守护进程 45 秒内用新代码重启（比杀进程省事，也不会漏掉正在处理的消息）。
